# 后端框架

Python 3.11+ 标准库实现。生产接入时保持十个业务模块边界，具体外部字段与协议只填入适配器。

## 模块职责

| 文件（`modules/`） | 职责 |
| --- | --- |
| `panel_api.py` | 面板请求校验、路由、配置和任务入口 |
| `external_client.py` | 分页、总量和完整性校验，限制最多 1000 页 / 10 万条 |
| `data_cleaner.py` | 调用领域标准化；验证唯一键、受管字段、值类型；同键同值合并，同键冲突拒绝 |
| `bitable_writer.py` | 生成计划，分批条件写入，逐条回读核验，保存检查点 |
| `warning_notifier.py` | 计算预警；根据本次配置决定发送；通知失败单独记录 |
| `scheduler.py` | 按日历计算执行日期，持久化待执行轮次，调用统一同步服务 |
| `sync_service.py` | 定时/应急统一编排、目标锁、快照、恢复与公开结果 |
| `agent_manager.py` | 已有工作流能力及权限检查 |
| `config_manager.py` | 配置校验、版本冲突检查、备份、原子替换 |
| `log_manager.py` | 固定安全事件、阶段与数量审计，INFO / DEBUG |

`models.py` 定义公共契约；`storage.py` 提供 SQLite 和进程锁；`adapters.py` 提供适配器注册及持久化模拟；`app.py` / `__main__.py` 负责应用装配与 HTTP 托管。支撑文件不计入十个业务模块。

## 数据与配置

一个数据目录内只有一个后端进程，操作系统文件锁在进程退出后释放。默认目录 `.local/backend/`；`--demo` 默认 `.local/demo/`。`--data-dir` 可覆盖。`--demo` 只决定新目录的初始配置，不会覆盖已有配置。

| 文件 | 内容 |
| --- | --- |
| `config.json` | 业务配置，唯一写入者为配置管理模块 |
| `config.json.bak` | 上次成功配置；出错时可人工核对恢复 |
| `config.json.pre-v2.bak` | 从分钟计划升级前的原配置；不会被日常保存覆盖 |
| `state.sqlite3`（含 WAL / SHM） | 任务、配置快照、标准化受管字段、操作计划、检查点、调度时间、日志 |
| `instance.lock` | 单进程文件锁 |

配置按版本修改：客户端提交读到的版本，旧版本返回 409。保存前全部校验，先写同目录临时文件并 fsync，再原子替换；失败保留旧配置。配置损坏时拒绝启动，不静默恢复成默认值。备份文件不是密钥仓库。

每个任务固定启动时配置和查询范围，包括恢复和通知重试。运行中修改配置只影响以后创建的任务。数据目录应使用服务账号的文件权限保护，不纳入 Git。备份应在停止服务后复制整个目录，或使用 SQLite 在线备份机制，不能只复制正在使用的主库而忽略 WAL。

## API

统一返回 `{ "ok": true, "data": ... }` 或 `{ "ok": false, "error": { "code": "...", "message": "..." } }`。异常堆栈、原始响应和认证信息不返回前端。所有时间以 ISO8601 UTC 序列化。`runId` 为不透明字符串。

| 方法 / 路径 | 请求 | 作用 |
| --- | --- | --- |
| GET `/api/exo/config` | — | 实际生效的配置、版本与更新时间 |
| POST `/api/exo/config/schedule` | `{version,value:{enabled,kind,time,timezone,...}}` | 接口 1：保存调度周期，重新计算下次执行时间 |
| POST `/api/exo/sync` | `{year:2024}` | 接口 2：异步创建应急任务，202 返回 `{runId}` |
| POST `/api/exo/config/warnings` | `{version,value:{intervals:[{minDays,maxDays}]}}` | 接口 3：保存左闭右开区间；同值表示单日；空数组关闭阈值匹配 |
| POST `/api/exo/config/notifications` | `{version,value:{enabled}}` | 接口 4：保存推送开关 |
| POST `/api/exo/config/integrations` | `{version,value:{mode,sourceUrl,workflowUrl,tableId,uniqueKey,managedFields}}` | 保存连接引用与受管字段 |
| POST `/api/exo/config/logging` | `{version,value:{level:"INFO"}}` | 切换 INFO / DEBUG |
| GET `/api/exo/status` | — | 状态、阶段进度、当前模式与集成就绪状态、最近任务数量 |
| GET `/api/exo/history` | `page&pageSize&state` | 任务结果、来源、年份、版本、阶段、数量、恢复及通知状态 |
| GET `/api/exo/diff/:runId` | `page&pageSize` | 仅已核验写入的受管字段展示差异；summary 为全量统计 |
| GET `/api/exo/logs` | `page&pageSize&level&category` | 操作审计；类别 config / sync / notification / schedule |
| POST `/api/exo/runs/:runId/resume` | `{}` | 202，恢复该任务的未完成部分 |
| POST `/api/exo/runs/:runId/notifications/retry` | `{}` | 202，单独重试已完成任务的失败通知 |

配置修改返回整个实际配置。分页从 1 开始，每页最多 100。冲突采用 409（例如 `SYNC_IN_PROGRESS`、`CONFIG_CONFLICT`、`RUN_SUPERSEDED`），参数错误 400，未知资源 404。

年份采用北京时间：历史年份 `[1 月 1 日, 次年 1 月 1 日)`；当前年份 `[1 月 1 日, 明日 0 点)`。范围以 `startInclusive` / `endExclusive` 交给适配器，未来年份不接受。自动同步固定查询当前年度，采用下面的日历规则，不再接受分钟间隔。

## 按日调度与提醒边界

配置格式为 `schemaVersion: 2`，修改计数仍使用 `version`。

所有调度参数都包含 `enabled`、`time`（严格 HH:mm）、`timezone: "Asia/Shanghai"`；默认每天 09:00，默认关闭。

| kind | 补充参数 | 行为 |
| --- | --- | --- |
| daily | 无 | 每天在指定时刻执行 |
| weekly | weekday: 1–7 | 周一为 1、周日为 7，固定星期和时刻 |
| monthly | monthDay: 1–31 | 固定每月日期；当月没有该日期时使用月末，下一月仍恢复原日期 |
| interval | intervalDays: 1–365，startDate: YYYY-MM-DD | 从指定日期起每隔 N 个自然日执行，停机和重启不改变锚点 |

保存时只安排严格晚于当前时间的轮次；已有安排重启后保留。其他分区的配置变更不会重置调度。下次时间仍以 UTC 返回，面板按北京时间显示。后端进程必须保持运行，关闭网页不影响执行。时区当前固定为北京时间。

提醒天数为非负整数。`[minDays,maxDays)` 包含左端、不包含右端；两值相同是一个单日规则。例如 `0–7` 命中 0 至 6，`7–7` 只命中 7；`0–7` 和 `7–14` 可相邻。单日 7 与 `7–14` 会重复命中，因此拒绝保存。界面校验、后端校验和实际预警计算使用相同口径。

升级已有配置时，先原子备份至 `config.json.pre-v2.bak`，再升级格式与版本。旧分钟计划停用并置为每天 09:00，需在面板重新确认开启；不猜测原分钟计划应换成哪一种日历周期。旧预警端点数值保留，新任务按新边界计算。历史任务的原始配置快照没有被改写，恢复时继续遵守其旧规则。升级失败时保留原配置并拒绝启动。

## 真实适配器接入边界

部署方提供一个可信 Python 工厂，返回 `(SourceAdapter, WorkflowAdapter)`，例如通过以下入口加载：

```sh
python -m backend --adapter-factory your_integration:create_adapters
```

工厂实现由部署方提供，仓库没有假定任何外部 API 的请求字段或飞书工作流协议。凭据通过服务端环境或密钥管理设施注入工厂，不能放在前端、连接 URL、公共配置或日志中。连接地址只接受无用户名、查询串和片段的 HTTP(S) URL；实际网络地址的部署白名单由适配器控制。

### 源端适配器

- `fetch_page(time_range, cursor, config) -> SourcePage`：实施真实协议的认证、超时、响应解析和有限的读重试。显式返回记录、稳定总量、下一页游标及完整性标志；拉取失败不得伪装成空列表或完整结果。若源端不能提供一致分页，应由适配器建立可靠快照或拒绝执行。
- `normalize(record, config) -> NormalizedRecord`：实现后续确定的清洗和业务筛选规则，输出不透明业务键、完整的受管字段投影、可选 `warning_days`。当前框架要求规范化结果每条有效；不符合规则会整体停止写入。业务筛选若需要丢弃记录，应在适配器明确实现并给出验收口径，不能静默跳过格式错误。
- 每个受管字段必须存在；值只接受 string / number / boolean / null，不接受原始对象。缺值与明确置空需由领域规则区分，避免用默认 null 意外覆盖。
- 展示字段本身必须可公开。框架拒绝敏感字段名，但不能判断普通字段中的内容是否敏感，适配器须先按业务白名单脱敏。

### 已有智能体 / 工作流适配器

- `check_access(config)`：检查目标表、字段及调用权限。
- `read(keys, config)`：完整返回请求的每个键；不存在为 null，读取不完整必须报错。读结果必须权威且足以核验受管字段，不能用异步任务的“已接收”响应充当写入成功。
- `write_batch(operations, config)`：每项含固定 `operationId`、业务 `key`、`before`、`after`。必须保证唯一键 upsert、操作 ID 幂等，并在实际写入点原子校验受管字段仍与 before 一致。只修改 after 的字段，保留其他字段。不支持条件更新的工作流需增加串行写入网关或版本校验；仅“先读后写”不满足防止并发覆盖要求。
- `notify(alerts, operation_id, config)`：按通知操作 ID 去重；返回前确认发送结果。超时可能已发送，重试时必须核验或去重。
- 必须声明并实际满足 `business_key_upsert`、`idempotent_operations`、`authoritative_read`、`conditional_write`；启用通知还需 `idempotent_notifications`。声明不能代替真实集成验收。
- 适配器的每个外部调用必须有有限超时，写入的单项/批次语义与结果回读必须经过故障注入验收。标准库框架不会强杀任意阻塞的第三方适配器线程；真实适配器尚未安装前无法验证外部超时与权限行为。

模拟适配器使用 id 作为唯一键，可管理 title / status / ageDays 字段，提供 12 条合成记录。模拟表格、操作去重表和通知去重表都保存在 SQLite；不会调用飞书。

## 可靠性规则与当前限制

同一 `mode + tableId` 在同一数据目录中仅允许一个同步任务处于运行态，SQLite 唯一索引约束定时和应急入口。跨多个数据目录或多台主机部署不共享锁；当前框架按单实例部署，不能当作分布式队列使用。

拉取完整数据并通过清洗校验后才生成计划。写入计划先持久化，再按 20 条分批执行。每批先核验当前值：已等于目标值则确认，不重复写；与计划的旧值一致则发出条件写入；其他情况停止覆盖。无论远端调用返回成功还是抛出异常，都逐条回读核验，只把核验一致的项标为已确认。

默认不执行删除。源端数量与总量不一致、分页循环、冲突唯一键、字段错误或目标回读不完整时停止相应链路。框架不为未经定义的业务“过滤不合格记录后继续写入”做假设。

进程启动时将未完成任务标为 interrupted，保留原计划和配置；用户在历史中恢复。恢复不会直接把全任务重新写一遍。如果计划尚未生成，可以重新拉取/清洗；如果计划已生成，只核验未确认项。目标已有更晚任务时拒绝恢复旧任务，防止旧计划覆盖新数据。

通知失败保留同步 success，并在 notificationState 独立标记；只重试通知不会重写表格。通知发送中重启后视为待核验失败。开启/关闭推送只影响后续任务，既有任务始终使用其快照。

调度先持久化待执行轮次，再使用固定轮次键创建任务，最后推进下次日期。SQLite 对轮次键建立唯一索引。若创建任务前中断，恢复后重试同一轮；若任务已创建而日期尚未推进，恢复后找到原任务，不重复创建。已创建但中断的任务仍通过任务恢复入口处理。停机跨过多轮时最多补一次，再回到原日历安排；同目标正忙则跳过该轮，首页及日志显示原因。仅保证当前单实例范围内的轮次去重，不是分布式调度系统。日志与任务成功记录也不是跨外部系统的分布式事务。

运行记录和检查点以 JSON 文档存入 SQLite，适合基础框架和中小数据量；当前历史查询读取所有运行文档后分页，大规模长期部署前应拆分明细表、索引摘要及定义保留策略。该限制不改变对外模块契约。

## 托管与生产边界

内置 HTTP 仅监听 `127.0.0.1`，用于本机运行和受控反向代理。POST 需要 JSON、`X-Requested-With: fetch`，校验 Origin 和 Host；不开放 CORS。公共响应与日志均使用固定安全字段和文案，未知异常不暴露堆栈。

**当前不包含用户登录、会话签发或多租户权限系统。** 对外部署前必须置于带身份认证与 HTTPS 的反向代理之后，并通过 `--allowed-origin https://your-console.example` 显式允许该来源及 Host；不可直接将本机端口暴露到公网。不要把真实凭据写入可回读的业务配置。

构建好的前端可由内置服务器托管：index 为 no-cache，哈希 assets 为 immutable，页面路由 fallback，API / admin 不做 fallback。也可以使用前端目录中的 Nginx 示例，并自行添加身份认证。

## 验收

`python -m unittest discover -s backend/tests -v` 覆盖版本冲突与保存失败、年份边界、同目标互斥、快照隔离、重复执行与人工字段保留、完整性校验、条件更新冲突、部分失败恢复、写入后崩溃重启核验、通知独立重试、日志字段白名单、HTTP 来源校验与 SPA fallback。

真实接入后必须使用真实测试表再验证：重复执行、源端分页变化、工作流部分成功、写后响应丢失、人工并发编辑、进程重启、通知响应丢失，以及与生产凭据权限一致的受控写入范围。模拟测试通过不等于真实工作流已达到这些保证。

## 本轮系统检查（2026-11-03）

以下结论来自现有代码、模拟适配器故障注入测试和页面联调，未包含真实飞书或外部系统的验收。

已修复：

| 问题 | 原先影响 | 处理 |
| --- | --- | --- |
| 调度按分钟滚动计时 | 不符合每天、每周、每月的固定日期安排，延迟会导致时刻漂移 | 改为固定北京时间的日历调度，保留每隔 N 天的日期锚点 |
| 预警采用闭区间 | 相邻范围无法共用边界，结果与业务期望不符 | 校验、计算、界面统一采用左闭右开；同值为单日 |
| 先推进下次时间，再创建任务 | 两步之间退出可能丢失该轮 | 持久化待执行轮次及唯一键，重启后重试或找到原任务 |
| 写入异常统一归为部分失败 | 条件冲突也显示可以恢复，容易反复点击无效恢复 | 回读发现冲突或适配器明确报告冲突时，停止恢复并提示核对 |
| 总览读取所有目标中的最近结果 | 更换目标表格后仍可能显示旧表格成功 | 状态、上次成功与数量按当前目标筛选；历史仍保留全部记录 |
| 审计异常中断任务登记或错误收尾 | 未实际执行的任务可能一直占用运行锁 | 启动失败明确落为 error；错误收尾不再依赖审计写入成功 |

上线前仍需处理：

| 优先级 | 当前缺口与证据 | 建议 |
| --- | --- | --- |
| 高 | 真实源端与工作流未实现；adapters.py 只有模拟实现和工厂入口 | 提供真实协议、业务唯一键与字段映射，在隔离测试表验证幂等、条件更新、部分失败、超时和权限 |
| 高 | app.py 只有来源检查，没有登录、角色授权；审计没有操作人 | 接入身份认证，区分查看、手动同步、配置管理权限，把操作人写入审计。折叠管理员设置不能作为权限控制 |
| 高 | 外部调用超时依赖适配器，线程没有可强制终止的执行边界 | 外部请求实现有限超时和重试预算，增加独立任务执行进程或监督机制，验收永久阻塞场景 |
| 中 | 面板只有预警数量和规则，没有预警记录读取接口、处理状态或表格定位入口 | 补预警清单及目标记录链接，明确哪些人接收、如何处理与避免重复提醒 |

| 中 | Store.runs() 每次读取完整历史 JSON，检查点反复写整份任务；futures 也持续保留 | 拆分任务摘要、操作明细和分页索引，清理完成的执行句柄，定义日志与历史保留策略并压测 |
| 中 | 当前需要手工启动后端；无服务托管、健康监测及自动备份恢复演练 | 部署为受监督服务，增加存活/调度延迟监测、完整数据目录备份和恢复演练；网页关闭与后端停机需区分 |
